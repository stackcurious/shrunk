## 5. What each override does, and where it hooks in

Everything lives in **`Shrunk/Support/UITestingOverrides.swift`**, gated on
`UITestingOverrides.isActive` — `ProcessInfo.processInfo.arguments.contains("-ui-testing")`
inside `#if DEBUG`, and a compile-time `false` in Release, so every call site
folds away in a shipping build. The launch argument is passed only by
`ShrunkUITests`.

| Override | Hook site | What it does |
|---|---|---|
| Pro entitlement | `StoreKitService.refreshEntitlements()` — one line at the top | `isProUser = UITestingOverrides.forcesPro`. Default true; `-ui-testing-pro 0` (the paywall pass) leaves it false. No `SKTestSession`, no StoreKit daemon. |
| Product load | `StoreKitService.loadProducts()` — one line at the top | Returns immediately with `loadError = nil`. Both products stay `nil`, which the paywall already treats as "still loading", so it renders the spec prices ($14.99 / $2.99 / "Save 58%") instead of the "Couldn't load plans" error state. Those are the same values in `Shrunk/Resources/Shrunk.storekit` and in the listing. |
| Trial eligibility | `StoreKitService.refreshTrialEligibility()` — one line at the top | `isTrialEligible = true`, so the paywall shows the 7-day trial affordances. |
| Kroger store | `UITestingOverrides.prepareDefaults()`, called first in `ShrunkApp.init()` | Writes `storeLocationId` / `storeName` — the exact two `UserDefaults` keys `StorePickerViewModel.select(_:)` writes — from `-ui-testing-store` / `-ui-testing-store-name`. Also sets `shrunk.has_completed_onboarding` and seeds `shrunk.recent_barcodes` from `-ui-testing-recent-a/b/c`. **Prices are never faked**: they come from `/v1/kroger/product` on the production Worker. |
| Alert fixtures | `UITestingOverrides.seedFixtures(container:)`, called in `ShrunkApp.init()` right after the `ModelContainer` | Deletes existing `ShrinkAlert` rows and inserts three: a `.sizeDrop` (Bounty Select-A-Size, 117 → 105, −10.3%), a `.priceHike` (Cheez-It Original) and a `.verifiedCase` (Toblerone 360 g → 150 g, −58.3%). Every figure is copied from `data/trending.json`'s verified cases. None carries a `currentPrice`, so the savings hero deliberately shows "Watching for sneaky shrinkflation" rather than a dollar figure it can't back up. |
| Contribution draft | `ContributeViewModel.init(...)` — a 6-line block at the end | Runs the **real** `NetContentParser.firstNetContent(in:)` over the real label line `"NET WT 12.5 OZ (354g)"` and lands on `.confirm`. The 354.369 shown in the sheet is the parser's own output, not a typed-in number. |
| Camera authorization | `BarcodeProcessor.bootstrap()` and `LabelCaptureController.bootstrap()` — one guard each | Report `isAuthorized = true, isRunning = true` and skip `AVCaptureSession` setup, so the real scanner / label chrome renders instead of the permission prompt. |
| Initial tab | `UITestingOverrides.prepareDefaults()` | `-ui-testing-tab <n>` seeds `shrunk.selected_tab` so the Alerts and paywall passes launch straight onto their tab. Tapping across from the dark scanner flips the window colour scheme, and the tab bar's material could still be mid-transition when the frame was grabbed. |
| Camera backdrop | `CameraPreviewUIView.init(session:)` + `layoutSubviews` + `refresh(session:)` | Paints a neutral dark `CAGradientLayer` instead of binding the capture session. `ScannerView` and `LabelCaptureView` are **not** modified for this — the substitution happens inside the existing `CameraPreviewLayer` seam. |

No view code was forked. Production behaviour with the argument absent is
unchanged: every hook is a single early-return guarded by a constant that is
`false` in Release.

## 6. Bug found and fixed while capturing (please review)

**The whole app window was being forced into dark mode by the scanner tab.**
`ScannerView` ended in `.preferredColorScheme(.dark)`. That is a *preference*,
which propagates out of the `TabView` to the window regardless of which tab is
visible — so Browse, Watchlist, Alerts and Settings all ran with a dark window
and drew the **status bar in white on the cream `Color.paper` background**,
i.e. effectively invisible. It was visible in the first capture pass
(`05_alerts.png` had an unreadable 9:41), and it is a real shipping defect, not
a simulator artifact.

Fix (2 lines, `Shrunk/Features/Scanner/ScannerView.swift` and
`Shrunk/ShrunkApp.swift`):

- `ScannerView` now uses `.environment(\.colorScheme, .dark)`, which scopes the
  dark styling (and the `.ultraThinMaterial` pills) to its own subtree without
  setting a window-level preference.
- `MainTabsView` sets `.preferredColorScheme(selectedTab == 0 ? .dark : .light)`,
  so the window follows the selected tab: dark on the scanner, light everywhere
  else.

This is the only change in this commit that alters production appearance.
Revert those two hunks if you disagree with the approach; the screenshots would
then need re-capturing with an unreadable status bar on 01, 05 and 06.

## 7. Screen-by-screen: what is on each shot, and what is not fully ideal

### 01 `01_result_shrunk.png` — Maxwell House Original Roast

Route: Scan tab → seeded RECENT chip `0043000071800` → `ResultView`.
All data from `GET /v1/product/0043000071800` on the production Worker (two
dated `curated` observations, sourced to mouseprint.org in D1).

Shows: **20% SHRUNK** meter · "They took 172.9 g" · THEN 867.5 g (2019) → NOW
694.6 g (2022) · the live-price panel headed **KROGER HYDE PARK / Prices from
Kroger** · the **SIZE HISTORY** card (BEFORE Dec 2019 → NOW Aug 2022).

> **Not ideal — and it is truthful.** The live-price panel reads *"Store prices
> unavailable right now / The verdict and size history above don't need them."*
> **No curated verified case in `data/trending.json` resolves to a priced item
> in Kroger's catalogue today.** I checked all 35 curated GTINs against
> `/v1/kroger/product` at 19 Cincinnati/Middletown store ids:
>
> - 32 of 35 return `not_found` — their UPCs are retired or simply wrong
>   (e.g. curated "Cheez-It Original Family Size" is `0024100762330`; Kroger's
>   actual 21 oz box is `0024100440702`, and the 76 ct Tide Pods case is
>   `0030772091654`, not the curated `0037000841548`).
> - `0080878194575` (Pantene) matches by identity but Kroger publishes **no
>   price** for it at any store, so the panel would render "—".
> - `0028400064057` ("Doritos Nacho Cheese") and `0028400090094` ("Tostitos
>   Scoops") *do* return a price, but for **different products** — Kroger maps
>   those UPCs to "Tostitos Bite Size Rounds 13 oz" and "Lay's Salt & Vinegar
>   1 oz". Putting those prices under a Doritos/Tostitos verdict would have been
>   a lie, so they were rejected.
>
> I also swept ~500 Kroger-priced GTINs looking for any product with two or more
> dated non-Kroger observations *and* a live price, so one screen could carry a
> real verdict and a real price together. There is exactly one match and it is a
> false positive (a 209 g box vs a "6 ct / 1.08 oz" multipack — a unit-parsing
> mismatch, not a shrink). **Today the two datasets do not overlap.** The
> honest options were "panel shows unavailable" or "no panel at all"; I chose the
> former because the listing table asks for the panel and the attribution.
>
> **If you want a fully green screenshot 1**, the fix is upstream, not here:
> correct the curated GTINs in `data/trending.json` to UPCs Kroger actually
> carries, re-seed D1 and redeploy the Worker. Both are out of scope for a
> screenshot task and neither takes effect without a backend deploy.

Also note: the earlier date renders as "2019 / Dec 2019" rather than Jan 2020 —
the stored observation is `2020-01-01T00:00:00Z` and the device is in US Central,
so it lands on 31 Dec 2019 locally. Cosmetic, and the same on a real device.

## 8. Other findings worth someone's attention (no action taken)

1. **Curated GTINs are wrong for a large share of `data/trending.json`.** 32 of
   35 do not exist in Kroger's catalogue, and at least two map to entirely
   different products. This does not just cost us a screenshot — with
   `KROGER_PERSIST=on`, opening one of those curated cards makes the app fetch
   `/v1/kroger/product/<curated gtin>` and the Worker writes the *wrong
   product's* size back as a `kroger` observation. `0028400064057` (curated
   Doritos 9.75 → 9.25 oz) now carries a stored 13 oz "kroger" observation from
   Tostitos Bite Size Rounds, and `/v1/product` for it returns
   `needs_confirmation: true`. Same for `0028400090094` (a 1 oz Lay's bag) and
   `0080878194575`. Those rows should be purged and the GTINs corrected.
2. **`/v1/feed` drops the earlier observation's date.**
   `TrendingFeedService.entry(from:bundled:)` synthesises the "then" date as
   `observed_at - 86400`, so a Browse card opened from the feed shows
   "2022 → 2022" for a 2020 → 2022 case. This is why screenshot 01 goes through
   the scan path instead of Browse.
3. **`ShrinkDetector`'s `insufficientData` branch sets `previousSize` and
   `currentSize` to the same record**, so a product with exactly one observation
   renders a "THEN 708.7 g → NOW 708.7 g" comparison row. The
   `costPerOzSection`'s "CURRENT SIZE" style card would read better there.
4. `docs/APP_STORE_LISTING.md` still says to capture "on a physical device …
   signed into a StoreKit sandbox account". These were captured on a simulator
   against the production backend, with Pro supplied by a launch argument. Worth
   updating that line, but it is the listing owner's doc so I left it alone.
