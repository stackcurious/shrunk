- **Tests stub fetch with `vi.stubGlobal`** plus `afterEach(() =>
  vi.unstubAllGlobals())` — followed exactly, no `fetchMock`.

Nothing reads `observations.confidence` as a filter anywhere in the Worker, so

### Migration `0007_observations_off_source.sql`

Checked against the **live** schema before touching anything
(`SELECT sql FROM sqlite_master WHERE tbl_name='observations'`):

- The rebuilt table is production's column-for-column, with `'off'` added to
  the `source` CHECK and nothing else changed. No column was dropped or
  reordered; `status`/`accepted` semantics and the `unit_kind` CHECK are
  identical.
- `obs_gtin` and `obs_source_ref` are the only other objects on the table — no
  triggers, no views — and both are recreated.
- Nothing in the schema references `observations` by foreign key, so the
  `DROP`/`RENAME` cannot orphan another table; `observations`' own
  `REFERENCES products(gtin)` is enforced during the copy, and a pre-flight
  count found **0 orphan rows**, so it could not trip.
- `AUTOINCREMENT` survives: ids are copied explicitly and SQLite carries
  `sqlite_sequence` through the rename (verified on a seeded local copy —
  seq 3 before, seq 3 after).

**Fixed in `aa8d47e`:** it was not re-runnable, which matters because wrangler
only records a migration once it succeeds — a half-applied file gets retried
by hand. Added `IF NOT EXISTS` on the scratch table and both indexes, and made
the scratch-clearing `DELETE` name `observations` in a guard subquery, so a
re-run inside the one-statement `DROP`→`RENAME` window fails to *prepare*
rather than deleting what is by then the only copy of the table. Both
properties were then exercised against a seeded SQLite copy with
`foreign_keys=ON`: clean run preserves rows/indexes/sequence, a full re-run is
a no-op, and the simulated crash-window re-run refuses without data loss.

## 2. The zero-observation gap (`aa8d47e`)

`GET /v1/product/:gtin` now runs the same FDC→OFF size backfill for a product
that already exists with `origin='lookup'` and no accepted observation.
Test-first: 6 new tests in `backend/test/lookup.test.ts`, 3 of which failed
against the pre-fix Worker (`expected null to be 'mass'`, `expected 0 to be
greater than 0`).

Guards, cheapest first: a product that already carries `unit_kind` issues no
query at all; everything else the decision needs (`origin`, `updated_at`, and
the accepted-observation count) is one `getProductLookupState` round trip; and
`products.updated_at` must be older than an hour. Every attempt calls
`touchProduct` **before** the upstream calls, so a burst of concurrent
requests, a fetch that throws, and a size that never parses all cost one pass
per hour rather than one per request. Nothing else in the Worker reads
`products.updated_at` (only `alerts.ts` and `admin-kroger.ts` touch `products`
at all), so bumping it is free.

Both paths now share one `lookupProduct`/`persistSize` pair. That also fixed a
smaller miss in the original: when FDC returned a name but no `packageWeight`,
the product used to land sizeless and OFF was never asked. OFF is now
consulted for the size in that case — still exactly one upstream request when
FDC does carry a size.

## 3. Extra bug found and fixed (`1add9a0`) — the FDC leg was mostly dead

FDC matches `query` against the `gtinUpc` string **exactly as stored**, and it
stores all three spellings. Of 50 sampled "Doritos" records: 26 fourteen-digit,
19 twelve-digit, 5 thirteen-digit. We only ever sent our canonical 13-digit
zero-padded form, so:

```
query=0016000362451   -> totalHits 0
query=00016000362451  -> totalHits 1
```

Roughly 90 % of the FDC catalogue was unreachable through the on-miss lookup —
the reason `origin='lookup'` products came back from Open Food Facts or not at
all, and the reason rule 6's FDC half had almost nothing to work with. Without
this, the backfill shipped in §2 would have called FDC and got nothing for
most GTINs.

`lookupFDC` now queries `gtinUpc:*<gtin with leading zeros stripped>`, which
matches every padding (verified against 12-, 13- and 14-digit stored records —
one hit each), and scans the page for the food whose `normalizeGTIN(gtinUpc)`
equals ours instead of assuming `foods[0]`, because a leading wildcard can also
match a longer gtin ending in the same digits. `pageSize` 1 → 5 for that.

## 5. Concerns / follow-ups

1. **`0052000338317` has no size anywhere upstream.** FDC does have the record
   (`00016000…`-style 14-digit id, found only via the fixed query) but its
   `packageWeight` is `null`, and OFF's entry carries no `quantity` field at
   all. The backfill fires and records the attempt; there is simply nothing to
   record. This product is spec §2's "No size at all" state and needs the
   label-capture CTA — not a backend bug.
2. **Two normalizer bugs, both out of scope here** (CLAUDE.md: a case goes into
   `fixtures/package_weights.json` first, then all three implementations —
   Python, TS and Swift — which means touching iOS files other agents are
   mid-edit on). Concrete fixture cases, ready to add:
   - *Mixed numbers.* FDC spells Doritos sizes `"9 1/4 OZ/262.2 g"`.
     `parsePackageWeight` splits on `/`, reads `4 OZ` (113.4 g) against
     `262.2 g`, sees them disagree beyond the 2 % tolerance and returns null.
     A miss, not a wrong answer — but it is why 3 of the 6 stuck products stay
     stuck. Expected: 262.2 g.
   - *Comma as equivalence, not addition* — **a latent correctness bug, not
     just a gap.** `"14.5 oz, 450 g"` (OFF's spelling for `0028400517799`)
     hits `parseSegment`'s "1 lb 4 oz" additive branch and returns
     **861.07 g** instead of 411.07 g. `SEGMENT_SPLIT` treats `/` and `()` as
     equivalence separators but not `,`. Any comma-separated equivalent pair —
     from Kroger sizes or crowd OCR as much as from OFF — can record a size
     roughly double the truth, which would later read as a fake "shrink".
   This is also why the backfill deliberately does **not** fall through to OFF
   when FDC returned a size that failed to parse: of the three products where
   that would apply, OFF would resolve two correctly (`"9.25oz (262.2 g)"`,
   `"5.125oz"`) and one wrongly (`"14.5 oz, 450 g"` → 861 g). A wrong size is
   worse than none, so that fallthrough should land together with the fixture
   fix, not before it.
3. **What the 6 stuck production products actually resolve to** once each
   one's hour elapses, given the deployed code: `0028400679077` gets a real
   observation (OFF `"10 oz"` → 283.495 g); `0052000338317` and
   `0036731002488` have no size anywhere upstream (see 1); `0028400516464`,
   `0028400700016` and `0028400517799` are blocked on the mixed-number case
   above. The much larger win is prospective — every future scan now reaches
   ~90 % more of FDC (§3).
4. **`.backend-lookup-report.md` is committed to the repo root** (in
   `5e27fb3`). Agent reports probably belong in `.gitignore` rather than in
   git history; not touched here, since the brief said not to rewrite history.
5. **`docs/RELEASE_CHECKLIST.md`** documents neither a migration list nor the
   lookup behaviour, so per the brief it needed no rewrite. The one place the
   change is visible is Step 4's `SELECT source, COUNT(*) … GROUP BY source`
   expectation, which got a one-line parenthetical naming `kroger`/`off`.
