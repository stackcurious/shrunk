## 1. The rules, as landed

Fixtures went in first (18 cases, `fixtures/package_weights.json` 35 → 53), all
three implementations failed the same 9 of them, then all three were changed in
the same commit. Rule order is identical in all three: **mixed numbers → leading
fraction → segment split → leading-count multiplier → prefer non-count, first
wins, same-kind segments must agree within 2 %**.

### R47 — `,` is an equivalence separator, never addition

`,` `/` `()` on a package all mean "the same quantity, said again". The split
regex handled `/` and `()` but not `,`, so `"14.5 oz, 450 g"` stayed one segment
and fell into `parseSegment`'s compound-imperial branch (the one that makes
`"1 lb 4 oz"` 566.99 g) — **861.07 g for a 411 g bag**. Any comma-separated
equivalent pair, from OFF, Kroger or crowd OCR, could record roughly double the
truth, and the next observation would read as a fake shrink.

```
\s*/\s*|\s*\(|\)\s*|\s*,\s+|(?<![0-9]),\s*
```

The two comma alternatives deliberately skip the **decimal and thousands comma**
of European spellings: a comma splits only when followed by whitespace, or when
not preceded by a digit. That matters — see §3: *every* comma in the 377 k
imported FDC rows is a decimal comma (`"360 g/12,7 oz"`, `"1,000 mL"`,
`"6,505 lb"`), and not one is a separator. Splitting them would have been a far
bigger regression than the bug being fixed.

### R48 — a mixed number is one quantity

`"9 1/4 OZ/262.2 g"` (FDC's spelling for Doritos) is 9.25 oz. Split on `/` first
it became the segments `"9 1"` and `"4 OZ"`, so the string either missed
outright (the 4 oz reading disagreed with the metric half by 131 %) or, with no
metric half to check it, **silently returned the fraction's denominator as the
size** — `"6 1/2 oz"` was stored as 2 oz, `"13 3/4 OZ"` as 4 oz. Expansion runs
before any splitting, and only for a proper household fraction (denominator
2/3/4/8), so FDC's mangled `"16 454/454 g"` and `"11/4 946/946 mL)"` are left
exactly as written.

### Third bug, found on the way: the pack count could be a decimal

Not in the brief, and worth more rows than either reported bug. A pack count is a
whole number, and `NetContentParser.swift` always required one
(`leadingBareInteger = ^(\d+)$`) — but Python and TS used
`^\d+(?:[.,]\d+)?$`, so they read `"8.8/249 g"` as an *8.8-pack* of 249 g and
stored **2191.2 g**; `"51.3/3.2 lbs/1.45 kg"` became 74.5 kg. All three are
integer-only now, which also removes a pre-existing three-way divergence, and is
what stops R48 from creating a new bug: `"4 1/4/120 g"` expands to
`"4.25/120 g"`, which under the old Python/TS rule would have become a 4.25-pack
of 120 g (510 g) instead of 120 g. Fixtured as such.

### Structural parity

Swift's leading-count branch looked only at `rawSegments[1]`; Python and TS
scanned every remaining segment and tolerance-checked same-kind repeats. Swift
now does the same, so the three read as line-for-line mirrors again.

## 4. Judgement call worth flagging

The brief gives `"14.5 oz, 450 g"` an expected value of **411.07 g**; the fixture
asserts **null (reject)** instead, and here is why.

14.5 oz is 411.07 g. 450 g is not — the two halves disagree by **9.5 %**, far
outside the ~3 % the brief itself names as the agreement condition (and outside
the normalizer's existing 2 % tolerance, which already rejects the identical
`"12 oz/500 g"` fixture). The brief's own parenthetical spells the rule out —
"the correct answer is one of them … and they should agree within ~3 %" — and
`861.07 = 411.07 + 450` suggests the "411.07" figure is the oz half of the
doubled reading rather than a considered expectation. Taking either half of a
disagreeing pair is a coin flip that can fabricate a shrink, and the backend
report's own conclusion was that a wrong size is worse than none.

**The reported bug is fixed either way**: `"14.5 oz, 450 g"` no longer returns
861.07 g. It returns nothing. And `"14.5 OZ, 411 G"` — the same pair when the
halves agree — is fixtured at 411.068 g, so the brief's expected number is
asserted where it is actually correct. If the product decision is instead "prefer
the metric half of a disagreeing pair", that is a one-line change to the
tolerance branch plus two fixture edits; say the word.

Two smaller notes:

- **Tolerance stays 2 %**, not the ~3 % the brief mentions. Every pattern in the
  brief agrees far inside 2 % (`1 L`/`33.8 fl oz` 0.04 %, `500 g`/`17.6 oz`
  0.21 %, `9.25 oz`/`262.2 g` 0.01 %, `1.5 LB`/`24 OZ`/`680 G` 0.06 %), so
  loosening the check would buy nothing and would only let more malformed rows
  through.
- **`"12 CT, 340 G"`-shaped strings now multiply** (→ 4082 g), because a
  comma-separated leading count goes through the existing R45 multipack rule,
  the same as `"12 ct / 340 g"` already did. That is the brief's instruction
  ("count vs mass decision consistent with existing rules") and it is what makes
  `"2 PACK, 8 OZ EACH"` and `"10 CT, 1.2 OZ EACH"` right, but a label that means
  "12 pieces, 340 g in total" would be overstated 12×. No such row exists in the
  imported FDC data (no comma is a separator there at all). If it shows up from
  Kroger or OCR, the fix is to require an explicit `EACH`/`PER` before treating a
  comma-separated count as a multiplier — a fixture case away, in all three.
