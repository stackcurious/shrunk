## 0. Headline

`shrink_detected` went **17/25 → 25/25** with no change to any data file.

The bug: verdicts were read off the **last two observations**. When a second
source reported *exactly* the size the previous observation already recorded,
the pair was `450 → 450`, `+0.0 %`, "Unchanged" — and the documented
`500 → 450` behind it was erased. Fage is the proof: USDA independently
confirms *both* of its endpoints and the product still read as never having
shrunk.

The rule, now spec §5.1: same-kind observations sorted by `observed_at` are
collapsed into **size runs** — consecutive observations agreeing within the
existing 1 % tolerance form one run — and the verdict compares the last two
runs. Each observation is tested against the value that **opened** its run, not
against its immediate predecessor, so sub-tolerance drift cannot accumulate
into one run spanning a real change.

## 3. Three judgement calls worth reviewing

**a. Verdict rules are not event rules — the digest and the sweep keep
comparing consecutive observations.** `weeklyCounts` asks "what shrank in the
last 7 days" and the sweep's `size_drop` asks "did this package change since
the last snapshot". Collapsing runs there would re-report the same shrink in
every weekly digest and re-fire the same push alert on every six-hourly sweep,
for as long as Kroger keeps observing the product. `previousAcceptedQuantity`
(raw, event) and `runPairEndingAt` (runs, verdict) now sit side by side in
`db.ts` with that distinction in both docstrings, and it is written into the
spec.

**b. `.unchanged` is now unreachable from `analyze`.** Adjacent runs differ by
more than the tolerance by construction, so `percentChange` is always outside
±1 %. The verdict band and the enum case are kept (the switches over it stay
exhaustive, and `WatchedProduct`/`ShrinkAlert` still carry the case), but
`ResultView`'s "Same size since 2021" line is now dead. That is the intended
trade: two observations of the same size, one of them a database agreeing with
the other about *today*, never justified a tracked-over-time "Unchanged" — it
is `.insufficientData`, and that is what the screen now says.

**c. Consequence found by grepping the consumers, not the types.** The
two-same-size-observations case moved from `.unchanged` into
`.insufficientData`, which makes `ResultView.sizeFactLine` — "946 ml, first
seen Feb 2018" — newly reachable for it. It dates from `currentSize.date`,
which for a single run would have been the *confirmation*, printing 2024 for a
size first recorded in 2018. Fixed at the source: the single-run branch keeps
the latest observation's quantity/unit/source but carries the run's **opening**
date, which is what "first seen" means. Test:
`test_measurementNoiseWithinToleranceStaysOneRun`.

**d. The Worker's feed clamp stays unconditional.** The app exempts same-source
pairs from the 0.25–4× plausibility clamp (a real shrink reported twice by one
source is the case the app exists to catch). `buildFeed`'s clamp, added a day
ago after `/v1/feed` published OREO Double Stuf as "−94.1 %", applies to every
database pair regardless of source. Left as-is — strictly more conservative
than the app, and it guards the path that publishes a claim to every Browse
tab. Noted as a deliberate divergence in spec §5.1.

## 4. Step 4 — the watchlist and alert baselines

Read and unchanged; both improve.

- `WatchlistService.add` takes its baseline from `record.currentSize`
  (`quantity`, `unit`). That is now the current run's size, and it is **stable
  across confirmations** — before, each new source agreeing within 1 % could
  nudge the stored baseline a future `size_drop` compares against.
- `recordScannedShrink` dedupes on `(barcode, currentSize.quantity)`. Same
  stability, so a re-scan after a confirming observation still cannot file a
  duplicate `.newShrink` alert. It also now fires at all for the eight curated
  products whose verdict used to be flattened to "Unchanged".
- `WatchedProduct.from`, `ShrinkAlert.newShrink/.sizeDrop` and
  `AlternativesEngine` read quantity/unit/unitKind only — no date pinning
  anywhere, so no test needed adjusting. `WatchlistSyncTests` builds
  `ShrinkRecord`s directly and is untouched.
- The history chart still draws `product.sizeHistory`, i.e. every observation —
  only the verdict pair changed.
